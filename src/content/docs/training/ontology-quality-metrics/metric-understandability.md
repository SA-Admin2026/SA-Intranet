# Things to consider

**Demographics**: Your content will be interpreted differently by each individual based on the terminology in which that individual has become accustomed to. Abstract terminology is always a trade-off for who may be able to interpret your content, in some cases this may be intentional or necessary. Inevitably, it should be expected that measurements of clarity/understandability to vary greatly.

**Time constraints**: Focusing on making something more clear/understandable can be exponentially time-consuming. This is more of a reason to go by some guide which allows you to quickly review.

# Aspects to measure

**Size**

- **Meaning**: How large the content is which implements a feature/functionality. Shorter is generally better unless it makes the content more ambiguous.
- **Includes**: Code; RDF Schema definitions; Documentation.
- **Positive**: Well-written Python code; A function implemented in less than 50 lines of code.
- **Negative**: A single function being implemented with 100’s of lines of code.

**Terminology**

- **Meaning**: Use of vocabulary in your definitions
- **Includes**: Words used in variables, functions, classes, documentation
- **Positive**: Use of common English terms; No ambiguity in phrases used.
- **Negative**: Use of abbreviations or shortened words; Multiple interpretations for phrases used.

**Conformance**

- **Meaning**: Use of external and internal standards.
- **Includes**: W3C standards; Widely used libraries; Gist.
- **Positive**: Making use of standards and libraries wherever possible.
- **Negative**: Making up unique syntax for a single purpose/task.

**Documentation**

- **Meaning**: Detailed descriptions explaining an implemented feature/functionality.
- **Includes**: Comments; skos definitions; API documentation.
- **Positive**: Covering all features/functionality in depth; No ambiguity in documentation.
- **Negative**: Descriptions having multiple possible interpretations
